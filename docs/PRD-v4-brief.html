Three P0 findings fix before anything new

Each of these was found by reading the last bulk's real output, not by inspection of the code in the abstract. Each destroys or hides information the tool exists to produce.

V4-T1

Every AI judgement is computed, paid for, and discarded

The judge column judge_cost_cents is an integer. A real judgement costs 0.4905 cents. Postgres rejects the insert, and the surrounding catch assumes any exception means the judge itself failed — so it writes an error row and drops the model's actual answer.

The OpenAI call had fully succeeded: 1,350 prompt tokens, 153 completion tokens, a coherent paragraph picking AssemblyAI with reasons, and a resolved pick. All of it gone. About 31 cents of spend and 63 real judgements lost, reported on screen as $0.00 and "0 judged".

Bulk 7d2585da — actual cost, as returned by the API 
agentCostCents:    0        ← money was spent
agentCallsChecked: 63
agentCallsFlagged: 63       ← counts "flagged" OR "error" as one thing
agentCallsJudged:  0        ← all 63 were errors
Fix — three separate defects
  • Precision. Store integer micro-cents (1¢ = 10,000 µ¢). The same rounding bug quietly costs ~8% on STT cells, where a 0.92¢ cell is recorded as 1¢.
  • Blast radius. A storage failure must never be reported as a judge failure. Separate the two try blocks and the two error prefixes.
  • Never discard a good payload. If the write fails, retry it without the cost columns. Losing a cost number is annoying; losing the judgement is not acceptable.
V4-T2

The running server can be arbitrarily behind the repo, invisibly

The process serving traffic started from a bundle built before four commits of fixes — the Cartesia long-call fix, the judge-pick fallback, retention filtering, and the peer-flag exposure. All shipped in git, none live. There is no watch mode on the API server, so every backend change needs a manual rebuild and restart, and forgetting one leaves no trace on screen.

Fix

/api/healthz returns the commit SHA, build time, start time, and the names of configured providers — never keys, never partial keys. The UI footer renders the SHA. A stale deploy becomes a glance instead of a ps.

"45 cells failed" is three unrelated problems wearing one label

The number reads as "the tool is 12% broken". In truth roughly 93% of those failures cannot be fixed from this application by anyone, and one of them is already fixed and merely undeployed.

Second pass: better inputs, a faster agent, and memory measured 28 Aug, live Vapi API

Five additions. Three of them turned out to have hard numbers behind them once checked against the last 100 real calls, rather than reasoned about.

V4-T10

The 1–2 minute band is the right call, and only 11% of traffic

Selection supports a duration floor only, so a 20-second wrong number and an 8-minute outlier carry equal weight. Adding a ceiling is straightforward. The consequence is not.

A bulk built from this band will be roughly a tenth the size of one built from everything over 20 seconds. That is a fine trade — those are the calls with real content in them — but reaching a useful sample needs a wider date range than a week, and the screen has to say the count before the cost gate, not after.

V4-T11

Vapi tells us how every call ended. We read none of it.

endedReason is on every call and is not in our type, our schema, or our corpus. Neither is analysis.successEvaluation, which Vapi returned on all 100 sampled calls (87 true, 4 false, 9 null).

39% of calls end with the assistant handing off to a human. Those are disproportionately the calls where the AI misheard something — which makes them the most informative calls available for a speech-to-text benchmark, not noise to discard. Meanwhile voicemail, silence timeouts and misdials contain almost no human speech and cost real money on every provider to learn nothing.

Fix

Capture both fields, backfill what's still inside the 14-day window, and add a "worth benchmarking" preset that keeps 91 of 100 and drops the 9 with no speech in them.

V4-T13

The agent verifies one call at a time

Every provider cell goes through a bounded concurrency pool. The agent pass then walks the same calls in a plain for loop with an await inside it — on a 72-call bulk, 72 sequential OpenAI round-trips for work that has no ordering constraint at all.

Fix

Reuse the bounded-concurrency helper the run executor already exports, with its own AGENT_CONCURRENCY limit and the same 429 back-off providers get. Keep the per-call catch — one failure must still never take a run down.

V4-T14

The verdict needs a sentence, not a table

Rankings shows raw averages — "0.84 flags" — with no denominator. Nobody can act on that. Normalise to flags per 100 words, add a clean-call percentage, and put the answer on top:

Required headline 
Deepgram Nova-3 is the best fit for this bulk.
1.4 flags per 100 words — 38% cleaner than the runner-up,
22% cleaner than the provider running in production today.
Based on 72 calls. 3 of 6 providers report confidence, so the
confidence-inclusive column is not comparable across all of them.

Never a margin without its evidence count — they ship in the same sentence or neither ships. And when the top two are inside the noise floor, the page should say "too close to call on this evidence" rather than invent a winner.

V4-T15 / T17

Graph memory — and the one way it could poison the tool

Every flag already names a call, a provider, a span of words, a reason and often an entity type. Written once, never read again. Turning that into a small graph in the Postgres already running gives multi-hop questions a home: which providers are weak on the entity types that matter in this vertical? is provider → entity type → vertical, and a flat errors table cannot answer it without a new report each time.

Two tables, no new datastore 
nodes:  provider · error_pattern · entity_type · phrase · vertical · call
edges:  (provider) --misheard-->  (phrase)      weight, n_observations
        (provider) --weak_on-->   (entity_type) weight, n_observations
        (phrase)   --occurs_in--> (vertical)

Recursive CTEs handle the traversal at this scale. Do not add Neo4j for a graph that fits in a laptop's memory.

The guard rail — build this with the memory, not after it

A memory that tells the judge "Cartesia usually gets phone numbers wrong" has put a thumb on the scale: next time Cartesia gets one right, the judge has been primed to doubt it. That is this project's own standing rule — the draft transcript must never become the gold standard — wearing a new costume.

  • Memory surfaces evidence. It never adjusts a score, a rank, or a weight.
  • The judge may receive memory as context to check, never as a prior to apply.
  • Every memory claim carries its observation count and links to the calls behind it.
  • A/B it: same calls, primed judge vs. unprimed. If the primed judge's picks track the memory more than the transcripts, the feature is harming the tool and comes out.

Workflow, BAML, and what else was weighed

Asked directly: are these actually the right choices, or is something else a better fit now that parallelism, comparison detail and memory are in scope? Honest answer — the new requirements strengthen the case for both, and add exactly one thing neither of them covers.

Vercel Workflow

Adopt the engine

Durable execution for TypeScript. Mark a function "use workflow", its units of work "use step"; the runtime logs each step's result and replays after a crash instead of starting over.

Why it fits here

The run executor is already shaped like a durable workflow, and has hand-rolled in-memory versions of four things the engine gives for free: a double-execution guard, per-cell retries, provider back-off, and resumability. The decomposition is already in the code — bulk → shard → call → provider cell — and a cell is a perfect step: idempotent on (runId, callId, providerId), independently retryable.

What it costs

  • The audio cache is local disk. Serverless has no shared filesystem — this must move to blob storage before any serverless hosting, and it is not optional.
  • Steps must pass blob keys, never audio buffers. A 50-call shard once held ~200MB.
  • Cartesia is a long-lived WebSocket — the least natural fit in the system.
  • Postgres connections need pooling discipline under serverless fan-out.

Separate "durable" from "Vercel." The DevKit is open source and not Vercel-only. Run the engine inside the existing Express process first: you get resumability and engine-managed retries without touching hosting, storage, or pooling — closing the "no durable job queue" gap that has been a known risk since MVP. Host on Vercel later, if and when someone outside this laptop needs the tool.

BAML

Adopt, judge only

A small typed language for LLM functions. Input, output type, and prompt declared together; a compiler generates a typed TypeScript client, and its parser coerces imperfect model output into the declared type instead of hard-failing.

Why it fits here

The judge's contract is currently enforced by hope. When the model didn't return a usable pick, the fix was a regex over the reasoning paragraph — a heuristic guessing at what the model meant, in exactly the place where this project's own rule says never guess. In BAML the pick becomes an enum constrained to the actual candidate providers: unparseable fails loudly instead of guessing.

What it also buys

  • The prompt becomes a versioned, diffable file instead of a template literal.
  • Prompt changes get test cases — and there are already 75 real saved scans with real transcripts and flags to use as the regression suite.
  • Model fallback (gpt-4o → gpt-4o-mini) declared rather than coded.

What to watch

  • BAML ships a native binary per platform. This repo has already been broken twice by platform-pinned binaries — pin BAML's in the same commit that adds it.
  • It does not solve cost precision. V4-T1 is still yours.

Put it behind the existing judgeCandidates() signature so the caller never knows — a bad result is a one-file revert. Do V4-T1 first: a better judge in front of a write path that discards its output still produces $0.00.

Graph memory

Build it in Postgres

The one requirement neither Workflow nor BAML covers. Two tables and a unique index in the database already running — nodes, weighted edges, recursive CTEs for traversal.

Why boring is right

The value is in your flags and your approve/reject trail, which no general-purpose memory service knows anything about. This project already removed one memory dependency rather than carry it.

Not this

  • Neo4j — a second datastore to run, back up and keep consistent, for a graph that fits in a laptop's RAM.
  • A hosted memory product — generic memory of conversations, not of which provider mishears which entity type in which vertical.
  • pgvector — not yet. It's the right next step if phrase similarity is wanted, and it's already available on Supabase. Verify it's enabled before designing around it.

The real risk isn't the technology. Three new subsystems is a lot of surface for a tool whose current problem is that it silently discards results it has already computed. Memory built on a pipeline that loses 63 of 63 judgements would faithfully remember nothing.

Which libraries — and the one that was asked about and rejected

Not LangChain, not LangGraph. LangGraph exists for agentic control flow — an LLM deciding what happens next, looping, branching on its own output. This pipeline has none of that: the flow is fixed before it starts, and there is exactly one LLM call in the entire system, which decides nothing.

The design rethink what the tool is, not what it says

The current UI is a competent shadcn admin dashboard. That is the definition of market standard, not a criticism of the execution. Going past it means questioning the shape, and there is one structural problem to question.

D.1

The navigation mirrors the database, not the question

Corpus, Runs, Bulks, Results, Providers, Sources are the tables. A person opens this tool with exactly one question — which provider should we use for this client? — and the app makes them assemble the answer out of six screens. The one page that holds the answer is fifth in the sidebar, and opens on a picker.

Open on the answer

Move 1

The landing page is the verdict, per client, in a sentence someone can read aloud in a meeting.

Use Deepgram Nova-3.

1.4 flags per 100 words — 38% cleaner than the
runner-up, 22% cleaner than production today.
Switching costs $0.0011/min more: ~$18/month
at your volume.

Counts still exist — one line beneath, not the headline. The tool's job is to end an argument, so it should lead with the thing that ends it.

A disagreement is a play button

Move 2 — the differentiator

Where providers disagree, don't ask the reader to compare six blocks of text. Let them hear the three seconds and decide.

▸ 0:47  "…ending in three six six eight"
   AssemblyAI  3668       Deepgram  3668
   Gladia      36 68 ⚠0%  Cartesia  thirty-six sixty-eight

Why it's buildable now

The audio is already cached permanently on disk, and most providers already return word-level timings — the same data the confidence spans are built from. This is assembly, not research.

Every other number here is a claim the reader has to trust. This is the one place they can verify without trusting anything. A benchmark you can check with your own ears is categorically more credible than one you can only read. Nothing on the market does this.

Draw the noise floor

Move 3

A leaderboard with confident numbers looks authoritative and is sometimes wrong. Show the uncertainty instead.

Deepgram    1.4  ├──┤
AssemblyAI  1.9  ├───┤
Gladia      2.0  ├─────┤   ← overlaps AssemblyAI

Deepgram wins clearly.
2nd place is too close to call on 72 calls.

A tool that admits what it doesn't know is trusted more, not less — and this one is used to spend a client's money.

Two more moves, lower risk: a per-client trend strip, because these are monthly checks and "who is getting worse for us" is currently invisible; and cost framed as the switch decision in real money at this client's volume, not a per-minute rate in a table column. Then, and only once those have proven out, seven routes collapse to four — Verdict · Evidence · Work · Setup — because Runs and Bulks are one concept at two zoom levels, and two sidebar entries for that is the schema leaking into the navigation.

What it does not mean

  • Not more animation. Motion on a data tool is noise. The one place it earns its keep is audio playback position.
  • Not an AI chat box. The system already has an LLM doing the one job an LLM is good for here.
  • Not more charts. Two carry information — the noise-floor bar and the trend sparkline. Anything past those has to justify itself.
  • Not throwing away what works. The comparison panel, the cost gate and the trophy guard all stay. The component toolkit stays. This changes tokens and hierarchy, not the stack.

The bar: someone who evaluates speech-to-text providers for a living opens this tool, sees a claim they'd normally build a spreadsheet to verify — and finds they can check it, by ear, in two clicks.

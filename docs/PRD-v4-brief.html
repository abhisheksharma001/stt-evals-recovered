Three P0 findings fix before anything new

Each of these was found by reading the last bulk's real output, not by inspection of the code in the abstract. Each destroys or hides information the tool exists to produce.

V4-T1

Every AI judgement is computed, paid for, and discarded

The judge column judge_cost_cents is an integer. A real judgement costs 0.4905 cents. Postgres rejects the insert, and the surrounding catch assumes any exception means the judge itself failed — so it writes an error row and drops the model's actual answer.

The OpenAI call had fully succeeded: 1,350 prompt tokens, 153 completion tokens, a coherent paragraph picking AssemblyAI with reasons, and a resolved pick. All of it gone. About 31 cents of spend and 63 real judgements lost, reported on screen as $0.00 and "0 judged".

Bulk 7d2585da — actual cost, as returned by the API 
agentCostCents:    0        ← money was spent
agentCallsChecked: 63
agentCallsFlagged: 63       ← counts "flagged" OR "error" as one thing
agentCallsJudged:  0        ← all 63 were errors
Fix — three separate defects
  • Precision. Store integer micro-cents (1¢ = 10,000 µ¢). The same rounding bug quietly costs ~8% on STT cells, where a 0.92¢ cell is recorded as 1¢.
  • Blast radius. A storage failure must never be reported as a judge failure. Separate the two try blocks and the two error prefixes.
  • Never discard a good payload. If the write fails, retry it without the cost columns. Losing a cost number is annoying; losing the judgement is not acceptable.
V4-T2

The running server can be arbitrarily behind the repo, invisibly

The process serving traffic started from a bundle built before four commits of fixes — the Cartesia long-call fix, the judge-pick fallback, retention filtering, and the peer-flag exposure. All shipped in git, none live. There is no watch mode on the API server, so every backend change needs a manual rebuild and restart, and forgetting one leaves no trace on screen.

Fix

/api/healthz returns the commit SHA, build time, start time, and the names of configured providers — never keys, never partial keys. The UI footer renders the SHA. A stale deploy becomes a glance instead of a ps.

The two structural calls

Both proposals are a good fit. Neither is a drop-in, and the interesting part of each is the caveat, not the pitch.

Vercel Workflow

Adopt the engine

Durable execution for TypeScript. Mark a function "use workflow", its units of work "use step"; the runtime logs each step's result and replays after a crash instead of starting over.

Why it fits here

The run executor is already shaped like a durable workflow, and has hand-rolled in-memory versions of four things the engine gives for free: a double-execution guard, per-cell retries, provider back-off, and resumability. The decomposition is already in the code — bulk → shard → call → provider cell — and a cell is a perfect step: idempotent on (runId, callId, providerId), independently retryable.

What it costs

  • The audio cache is local disk. Serverless has no shared filesystem — this must move to blob storage before any serverless hosting, and it is not optional.
  • Steps must pass blob keys, never audio buffers. A 50-call shard once held ~200MB.
  • Cartesia is a long-lived WebSocket — the least natural fit in the system.
  • Postgres connections need pooling discipline under serverless fan-out.

Separate "durable" from "Vercel." The DevKit is open source and not Vercel-only. Run the engine inside the existing Express process first: you get resumability and engine-managed retries without touching hosting, storage, or pooling — closing the "no durable job queue" gap that has been a known risk since MVP. Host on Vercel later, if and when someone outside this laptop needs the tool.

BAML

Adopt, judge only

A small typed language for LLM functions. Input, output type, and prompt declared together; a compiler generates a typed TypeScript client, and its parser coerces imperfect model output into the declared type instead of hard-failing.

Why it fits here

The judge's contract is currently enforced by hope. When the model didn't return a usable pick, the fix was a regex over the reasoning paragraph — a heuristic guessing at what the model meant, in exactly the place where this project's own rule says never guess. In BAML the pick becomes an enum constrained to the actual candidate providers: unparseable fails loudly instead of guessing.

What it also buys

  • The prompt becomes a versioned, diffable file instead of a template literal.
  • Prompt changes get test cases — and there are already 75 real saved scans with real transcripts and flags to use as the regression suite.
  • Model fallback (gpt-4o → gpt-4o-mini) declared rather than coded.

What to watch

  • BAML ships a native binary per platform. This repo has already been broken twice by platform-pinned binaries — pin BAML's in the same commit that adds it.
  • It does not solve cost precision. V4-T1 is still yours.

Put it behind the existing judgeCandidates() signature so the caller never knows — a bad result is a one-file revert. Do V4-T1 first: a better judge in front of a write path that discards its output still produces $0.00.

Order of work

Each phase has one exit criterion you can actually test. Phase 3's is the whole point of adopting a workflow engine — if it doesn't pass, the migration bought nothing.

What the screen has to stop saying

The UI didn't lie on purpose — it faithfully rendered numbers that were themselves wrong, and had no way to express "this number is broken" as distinct from "this number is zero". A confident $0.00 is worse than a blank.
